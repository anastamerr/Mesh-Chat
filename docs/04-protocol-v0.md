# Protocol v0 Design

**Status:** Frozen Phase 0 packet, cryptographic binding, and private-envelope formats
**Last updated:** 2026-08-14

This document captures the logical protocol required for the first experiment. The routed-packet header, cryptographic bindings, private-message envelope, and Kotlin–Swift vectors are frozen for Phase 0 testing. BLE fragmentation remains open until its dedicated experiment passes.

## Frozen routed-packet header

All multi-byte integers use big-endian network byte order.

| Offset | Size | Field |
|---:|---:|---|
| 0 | 2 | Magic bytes `DM` |
| 2 | 1 | Protocol version (`0`) |
| 3 | 1 | Packet type |
| 4 | 1 | Flags; must be zero in v0 |
| 5 | 1 | Hop limit |
| 6 | 1 | Copy budget |
| 7 | 1 | Reserved; must be zero |
| 8 | 16 | Message ID |
| 24 | 16 | Temporary recipient routing token |
| 40 | 8 | Creation time in Unix epoch milliseconds |
| 48 | 8 | Expiration time in Unix epoch milliseconds |
| 56 | 4 | Unsigned payload length, bounded to 16 KiB |
| 60 | variable | Opaque encrypted payload |

The codec currently supports private-message and delivery-acknowledgement packets only. New packet types require explicit protocol work rather than speculative placeholders.

The canonical golden vector lives in `mesh-protocol/src/test` and is the compatibility source of truth for future Swift decoding.

## Design rules

- Private message plaintext is visible only to sender and recipient.
- Relay behavior operates on authenticated metadata and opaque ciphertext.
- Packets are bounded, versioned, expiring, and deduplicable.
- Messages may arrive out of order or through multiple routes.
- User-visible processing is idempotent.
- Acknowledgements can travel over a different route from the message.
- The protocol must not assume a continuously connected end-to-end path.

## Logical packet types

- `HELLO`: protocol and capability negotiation on an established link
- `PRESENCE`: announces a reachable temporary peer identity
- `PRIVATE_MESSAGE`: encrypted application payload
- `DELIVERY_ACK`: recipient-authenticated delivery acknowledgement
- `READ_ACK`: optional and deferred until after Phase 1
- `FRAGMENT`: one piece of a larger logical packet
- `QUEUE_OFFER`: advertises bounded store-and-forward capability
- `QUEUE_TRANSFER`: transfers an eligible sealed relay item
- `ERROR`: local link-level rejection without sensitive details

Phase 1 may combine some control packets internally, but packet type meanings must remain explicit.

## Logical envelope

Every routed packet requires the equivalent of:

```text
protocolVersion
packetType
messageId
createdAt
expiresAt
hopLimit
copyBudget
temporarySourceId
recipientRoutingToken
payloadLength
encryptedPayload
authenticationData
```

The production protocol should minimize or conceal identifying metadata. Stable public identity, group membership, nickname, and social graph information must not be broadcast as ordinary discovery data.

## Message identifiers

- Generated by the originating sender with sufficient randomness.
- Treated as opaque values.
- Never reused for another logical message.
- Used for deduplication, acknowledgement binding, and retry cancellation.
- Stored only for the bounded period needed by retention and replay policy.

## Forwarding v0

The first algorithm is controlled forwarding rather than global route calculation:

1. Deliver directly when the destination is connected.
2. Otherwise, offer the packet to eligible peers when hop limit and copy budget permit.
3. Decrement the hop limit for each relay operation.
4. Divide or consume copy budget according to the Phase 1 configuration.
5. Reject packets that are expired, malformed, over quota, or already seen.
6. Apply randomized forwarding jitter to reduce synchronized duplicates.
7. Preserve one eligible local copy until acknowledgement, expiry, or policy eviction.

Adaptive encounter scoring is intentionally postponed until real traces exist.

## Deduplication

Each device maintains two bounded indexes:

- **Network seen set:** suppresses recently forwarded packet duplicates.
- **Delivered message set:** prevents the application from displaying a logical message twice.

The delivered set must live at least as long as the maximum supported message retention window. Eviction rules must be explicit and tested.

## Acknowledgement semantics

A delivery acknowledgement contains or authenticates:

- Original message ID
- Recipient identity or verifiable recipient proof
- Acknowledgement type
- Creation time
- Optional protocol version and status

The sender clears delivery retries only after verifying the acknowledgement. Relays may forward acknowledgements and delete their associated copies, but cannot manufacture a valid delivered state.

## Fragmentation

Fragmentation occurs below the logical message layer:

- Each fragment identifies its parent packet and index.
- Total fragment count and reassembled size are bounded.
- Incomplete assemblies expire quickly.
- Memory allocated for concurrent assemblies is capped.
- Authentication must cover the final logical packet, not only individual transport fragments.

Exact fragment size will be chosen from measured BLE payload capabilities.

## Queue policy

Phase 1 configuration must define:

- Maximum message payload
- Maximum total relay bytes
- Maximum items per source or trust class
- Default and maximum retention
- Maximum retry count or retry schedule
- Hop limit
- Copy budget
- Deduplication retention
- Fragment assembly limits

No queue may grow without a hard byte and item bound.

## Cryptography decision gate

Protocol v0 must use an established authenticated key-agreement and encryption construction implemented by a maintained library. The implementation must not assemble raw primitives into an original cryptographic protocol without review.

Before selection, compare candidates for:

- Android maintenance and API compatibility
- Authenticated asynchronous messaging support
- Forward secrecy for live sessions
- Safe sealed delivery when the recipient is offline
- Test-vector availability
- License compatibility
- Cross-platform Swift support or reproducibility

### Private-message cryptographic format v0

The selected Phase 0 suite is RFC 9180 base-mode HPKE using X25519/HKDF-SHA256/AES-256-GCM, with Ed25519 authenticating the sender inside the encrypted envelope.

HPKE key-schedule context contains a domain, protocol version, packet type, message ID, recipient routing token, and creation/expiration times. Hop and copy budgets are excluded because relays must change them without breaking end-to-end authentication.

The signed private-message content contains a separate domain, the same immutable metadata, the recipient's raw 32-byte X25519 public key, the sender's raw 32-byte Ed25519 public key, the plaintext length, and plaintext. The signed content is sealed inside HPKE.

The decrypted envelope is:

| Offset | Size | Field |
|---:|---:|---|
| 0 | 1 | Protocol version (`0`) |
| 1 | 32 | Raw Ed25519 sender public key |
| 33 | 64 | Ed25519 signature |
| 97 | 4 | Unsigned plaintext length, big-endian |
| 101 | variable | UTF-8 application plaintext |

The maximum plaintext is 16,235 bytes so the 101-byte envelope, 32-byte X25519 encapsulation, and 16-byte AES-GCM tag fit the routed packet's 16 KiB payload bound.

Delivery acknowledgements sign a distinct domain plus protocol version, acknowledgement type, original message ID, sender routing token, and acknowledgement timestamps. Signature byte equality is never a protocol invariant; implementations verify signatures because valid Ed25519 implementations may randomize signing.

Raw X25519 and Ed25519 keys are exactly 32 bytes. Tink keyset serialization is neither a wire format nor an interoperability contract. Frozen bidirectional Tink/CryptoKit vectors live in `test-vectors/crypto-v0.properties`.

## Versioning

- Every connection negotiates supported protocol versions.
- Unknown mandatory fields or packet types fail closed.
- Experimental fields are explicitly namespaced or feature-negotiated.
- A protocol version is never silently reinterpreted.
